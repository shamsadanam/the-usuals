# Authentication & Login Flow

This pattern demonstrates how to implement secure, production-grade user authentication in a Nuxt 4 application using `nuxt-auth-utils`, an imperative `$api` plugin, and route middleware guards.

## Prerequisites

### 1. External Modules & Libraries
- **[`nuxt-auth-utils`](https://github.com/atinux/nuxt-auth-utils)**: Handles encrypted session cookies and authentication state.
  ```bash
  pnpm add nuxt-auth-utils
  ```
  Register in `nuxt.config.ts`:
  ```ts
  export default defineNuxtConfig({
    modules: ["nuxt-auth-utils"],
  });
  ```

### 2. Environment Variables & Runtime Config
- **Session Secret**: Add a 32+ character secret to `.env`:
  ```env
  NUXT_SESSION_PASSWORD="a-long-random-string-at-least-32-characters"
  ```
- **Runtime Config**: Configure API base URL in `nuxt.config.ts`:
  ```ts
  export default defineNuxtConfig({
    runtimeConfig: {
      public: {
        apiBaseUrl: process.env.NUXT_PUBLIC_API_BASE_URL || "https://api.example.com",
      },
    },
  });
  ```

### 3. Custom Application Files
- **Imperative Plugin**: **[`$api` Plugin](/nuxt/plugins/api)** (`app/plugins/api.ts`).
- **Route Guard Middleware**: `app/middleware/logged-in.ts`.
- **Session-Seal Server Endpoint**: `server/api/auth/session.post.ts`.
- **TypeScript Type Augmentation**: `types/auth.d.ts` augmenting `#auth-utils`.

## Key Architectural Concepts

1. **Browser-Egress Authentication**:
   - The browser POSTs credentials directly to the backend API (`/login`).
   - Avoids passing credentials through intermediate server functions unnecessarily.
2. **Encrypted HTTP-Only Session Cookie**:
   - On successful backend login (`{ token, user }`), the client sends the session payload to local Nitro endpoint `/api/auth/session` to seal an encrypted HTTP-only cookie via `useUserSession()`.
3. **Route Guard Middleware**:
   - `logged-in.ts` middleware verifies `session.value` before granting access to protected routes like `/dashboard`.
4. **Auto-Attaching Bearer Interceptor**:
   - `$api` plugin injects `Authorization: Bearer <token>` when requests set `{ auth: true }` and automatically logs out on `401` status responses.

## 1. Login Form Implementation (`app/pages/login.vue`)

The login flow performs three distinct steps:
1. **Direct Backend POST**: Posts user credentials directly to the external authentication backend.
2. **Local Session Seal**: POSTs the resulting `{ user, token }` payload to the local Nitro endpoint `/api/auth/session` to seal the encrypted HTTP-only cookie.
3. **Reactive Refresh**: Calls `fetchSession()` to update reactive `useUserSession()` state, then redirects to `/dashboard`.

```vue
<script setup lang="ts">
definePageMeta({ layout: false });

const { loggedIn, fetch: fetchSession, clear: clearSession } = useUserSession();
const { $api } = useNuxtApp();

if (loggedIn.value) await navigateTo("/dashboard");

const form = reactive({ email: "", password: "" });
const pending = ref(false);
const errorMsg = ref("");

async function onSubmit() {
  pending.value = true;
  errorMsg.value = "";
  try {
    const res = await $api<{ status_code: number; data?: { token: string; user: any } }>("/login", {
      method: "POST",
      body: { ...form }
    });

    if (res.status_code !== 200) {
      errorMsg.value = "Login failed.";
      await clearSession();
      return;
    }

    const { token, user } = res.data ?? {};

    await $api("/auth/session", {
      baseURL: "/api/",
      method: "POST",
      body: { user, token, loggedInAt: Date.now() }
    });

    await fetchSession();
    await navigateTo("/dashboard");
  } catch (e) {
    errorMsg.value = "Something went wrong.";
    await clearSession();
  } finally {
    pending.value = false;
  }
}
</script>
```

## 2. Route Guard Middleware (`app/middleware/logged-in.ts`)

```ts
export default defineNuxtRouteMiddleware(async () => {
  const { loggedIn, session, fetch: fetchSession } = useUserSession();

  if (!session.value) await fetchSession();
  if (!loggedIn.value) return navigateTo("/login");
});
```

To guard any protected page, add `definePageMeta({ middleware: "logged-in" })` at the top of the Vue component.

## 3. Imperative `$api` Plugin (`app/plugins/api.ts`)

Configures `$fetch` with the runtime API base or proxy endpoint, automatically attaches Bearer tokens when `auth: true` is passed, and handles automatic logout on `401` status responses. For full standalone details, see the dedicated **[$api Plugin](/nuxt/plugins/api)** documentation.

> [!NOTE]
> Interceptors run outside the Nuxt application context. Wrap composable calls like `fetchSession()`, `clearSession()`, or `navigateTo()` with `nuxtApp.runWithContext()`.

```ts
export default defineNuxtPlugin((nuxtApp) => {
  const { session, fetch: fetchSession, clear: clearSession } = useUserSession();
  const config = useRuntimeConfig();

  const baseURL = config.public.enableProxy
    ? "/api/proxy"
    : (config.public.apiBaseUrl as string);

  const api = $fetch.create({
    baseURL,
    headers: { Accept: "application/json" },

    async onRequest({ options }) {
      const { auth } = options as { auth?: boolean };
      if (!auth) return;

      if (!session.value) {
        await nuxtApp.runWithContext(() => fetchSession());
      }
      if (session.value?.token) {
        options.headers.set("Authorization", `Bearer ${session.value.token}`);
      }
    },

    async onResponseError({ response }) {
      if (response.status === 401) {
        await nuxtApp.runWithContext(async () => {
          await clearSession();
          await navigateTo("/");
        });
      }
    }
  });

  return { provide: { api } };
});
```

## 4. Session Seal Server Endpoint (`server/api/auth/session.post.ts`)

A thin Nitro route that seals the already-authenticated browser payload into the encrypted `nuxt-auth-utils` cookie without requiring server egress to the upstream backend.

### Architectural Rationale & Constraints

- **Why it exists**: In architectures where the Node/Nitro process cannot egress to the upstream backend (only the client browser can reach it), the standard pattern of server-side login calls is impossible. Instead, the browser authenticates directly with the backend and forwards `{ user, token }` here to seal the cookie.
- **Strict Allowlisting**: The client can submit arbitrary payloads, so only explicitly recognized fields (`user`, `token`, `loggedInAt`) are extracted. Never spread the raw `body` directly into session storage.
- **Deep Merging**: `setUserSession()` deep-merges with the existing session, meaning updates that only provide `{ user }` (e.g. profile changes) keep the active session token intact.
- **Cookie Security**: The session cookie is signed and encrypted using `NUXT_SESSION_PASSWORD` (minimum 32 characters) so it cannot be forged or inspected by the client.

```ts
export default eventHandler(async (event) => {
  const body = await readBody(event);

  const { user, token, loggedInAt } = body ?? {};
  const data: Record<string, unknown> = {};
  if (user !== undefined) data.user = user;
  if (token !== undefined) data.token = token;
  if (loggedInAt !== undefined) data.loggedInAt = loggedInAt;

  await setUserSession(event, data);

  return { status_code: 200 };
});
```

## 5. TypeScript Session Augmentation (`types/auth.d.ts`)

Augments the module `#auth-utils` to ensure `session.user` and `session.token` are typed throughout `useUserSession()` calls to match the backend payload.

```ts
declare module "#auth-utils" {
  interface User {
    id: number;
    name: string;
    email?: string;
    is_password_change_required?: boolean;
    [key: string]: unknown;
  }
  interface UserSessionData {
    token: string;
    loggedInAt: number;
  }
}

export {};
```
